\begin{abstract}
Engineers choose message brokers, which pass data between programs, partly by benchmarks
reporting latencies below a millisecond. At that scale, when a program reads the clock matters.
A broker acknowledges each message to the producer and delivers it to the consumer, two readings
on one machine's clock. Read as a latency, their difference understates end-to-end latencies
several-fold and distorts broker comparisons. Measured, it spreads over milliseconds; part falls
below zero. On one broker the acknowledgment arrives first, and there the cause is scheduling:
the thread reading it can wait for a processor core longer than the message takes to reach the
consumer. The other broker often delivers first. The rate of values below zero obeys laws we
derive and test by manipulation: it rises with processor load, whose placement matters, falls
when clock-reading threads get real-time priority, and falls on longer paths, on the timescale of
the scheduler's slice. An industry-wide audit finds such values discarded uncounted or never
measured, and a millisecond-clock filter deleting the fastest messages. Kernel timestamps, read on
a tool's own Linux sockets, exclude those threads' wait at modest rates. We give benchmark authors
and readers practical checks and measure what most buy.
\end{abstract}

\IEEEraisesectionheading{\section{Introduction}\label{sec:intro}}

\IEEEPARstart{M}{any} online services move their data through a message broker, a service
that takes each message from the program that publishes it, the \emph{producer}, and delivers it
to the program that receives it, the \emph{consumer} (Fig.~\ref{fig:model}a). Engineers choose
among brokers partly by latency benchmarks~\cite{openmessaging2018}, which time each message
from producer to consumer and now report latencies below a millisecond~\cite{redis_streams}. At
that scale, a thread's wait for a processor core can exceed the latency itself. A team that ranks
brokers or promises a response time on such a number may be acting on how the number was
measured, not on the broker. This paper shows how to separate the two and measure the broker
alone.

The stakes reach beyond any one benchmark. Delays of microseconds now shape how datacenter
systems are built~\cite{barroso2017killer}, and a large service is only as fast as the slowest of
its many parts~\cite{dean2013tail}, so its designers need latencies they can trust. Yet
experiments on computer systems can produce wrong data with nothing obviously
wrong~\cite{mytkowicz2009wrong}, a concern across the sciences~\cite{baker2016reproducibility}.
Timed from the broker's acknowledgment, as our first benchmark did, a message's latency
understates its trip from producer to consumer several-fold and distorts broker comparisons
(Section~\ref{sec:cost}).

We study one difference. Once the broker has written a message, it returns an acknowledgment to the
producer and delivers the message to the consumer. Let the producer and the consumer run on one
machine and read its one clock. The producer reads the acknowledgment at $t_{\mathrm{ack}}$, the
consumer reads the message at $t_{\mathrm{recv}}$, and on a broker that acknowledges first the two
should come in that order, apart only by a small positive margin, the time the message still
needs to reach the consumer.
We make four contributions.
\begin{enumerate}
\item \textbf{The distribution} (Section~\ref{sec:finding}). On one clock, $S = t_{\mathrm{recv}}
- t_{\mathrm{ack}}$ is spread over milliseconds, and $\spanNegAckPct\%$ of it falls below zero.
Nothing arrived early: no latency timed from the \emph{publish call}, the moment the producer
hands the message over, falls below zero.
\item \textbf{The mechanism, and its laws} (Section~\ref{sec:mechanism}). A thread must wait for
a core before it can read the clock. On \kafka{}, whose acknowledgment the kernel timed arriving
first, the thread that reads it can wait longer than the message takes to reach the consumer,
while \redis{} often delivers first and needs no wait. The rate of values of $S$ below zero rises with processor load
and depends on the load's placement, falls on longer paths, and has the timescale
of the scheduler's slice, set by the CPU count. \emph{Real-time priority}
runs the threads that read the clock ahead of every thread at the default \emph{normal
priority}. In every matched pair, real-time priority cut that rate at least $\rtKafkaLowerBound$-fold
on \kafka{} and $\rtRedisLowerBound$-fold on \redis{}, at unchanged \emph{background load}, the
processor work run beside the clients.
\item \textbf{The industry-wide audit} (Section~\ref{sec:external}). Of the \harnessMessageWord{}
message tools we read at source, \harnessMessageCutAllWord{} cut such values out of a figure they
report, and all but one, the Storage Benchmark Kit (SBK), count none. Under the strictest
reading of our classification, \auditStrictWord{} still cut them. Of the \toolsRunWord{} tools we
ran, \toolsOneProcessWord{} take both timestamps in one process, where no clock offset can reach
them. But \toolsOneProcessTripWord{} of those time a round trip and \toolsOneProcessAckWord{} only the
acknowledgment, neither of which is a delivery's \emph{one-way latency}, its time from sender to
receiver~\cite{rfc7679}, and the rest cannot see a separate receiving process's wait. On a
millisecond clock, a filter that keeps only latencies above zero, a \emph{positivity filter}, also
deletes the fastest messages, and no public report we audited says how many samples it kept.
\item \textbf{What to do} (Section~\ref{sec:practice}). Checks for benchmark authors and
readers, each with what it buys where we measured it, and one fix for a Linux tool. The fix times
each message between the kernel's timestamps as it leaves the client machine and arrives back,
which a tool can read on its own sockets in four steps. That latency held still across background
load and priority at fifty messages a second on one pair of machines, its median within the
$\fullFixMedianMarginPct\%$ set in advance, and agreed with packet captures up to $\osTopRate$ a
second.
\end{enumerate}
Together these show that a broker latency below a millisecond describes both the broker and how
it was timed, and they give the means to time the broker alone.


\section{How a Message Is Timed}
\label{sec:sysmodel}
\label{sec:method}

A producer process publishes messages to a broker at a paced rate, and a consumer process reads
them back. Each message crosses two legs (Fig.~\ref{fig:model}a). Leg~1 carries it to the
broker, which writes it to its log and returns an acknowledgment along leg~1, and leg~2 carries
it on to the consumer. Three timestamps bracket its path: $t_{\mathrm{pub}}$, read immediately
before the publish call; $t_{\mathrm{ack}}$, read when the producer learns that the broker has
accepted the message; and $t_{\mathrm{recv}}$, read when the consumer holds it. We call any
difference of two timestamps a \emph{span}. Three spans follow:
\begin{equation}
\begin{aligned}
D &\equiv t_{\mathrm{recv}} - t_{\mathrm{pub}}, \qquad
A \equiv t_{\mathrm{ack}} - t_{\mathrm{pub}}, \\
S &\equiv t_{\mathrm{recv}} - t_{\mathrm{ack}} \;=\; D - A .
\end{aligned}
\label{eq:model}
\end{equation}
Broker benchmarks call $D$ the \emph{end-to-end latency}, the message's time from the publish
call to the consumer, and $A$ the \emph{publish latency}, the producer's wait to hear that the
broker has it~\cite{openmessaging2018}. $S$ compares the acknowledgment's return along leg~1 with
the message's trip along leg~2. On \kafka{} the broker returns the acknowledgment before it answers
the consumer's waiting request. \redis{} writes the delivery to a waiting consumer first. Some
brokers can deliver a message before confirming it (Supplement~S3.6). A benchmark that starts
its clock at the acknowledgment, as our
own first one did, reports $S$ as the message's latency, and every publish latency carries
whatever delays the reading of its acknowledgment (Section~\ref{sec:toolsrun}). Two more readings
place a message in its workload: $t_{\mathrm{sched}}$, when the replayed schedule made it due, and
$t_{\mathrm{out}}$, when the consumer had handled it. The \emph{event-time latency}
$E = t_{\mathrm{out}} - t_{\mathrm{sched}}$ holds $D$, with the \emph{publish delay}
$t_{\mathrm{pub}} - t_{\mathrm{sched}}$ before it and the consumer's \emph{processing-time
latency} $t_{\mathrm{out}} - t_{\mathrm{recv}}$ after it~\cite{karimov2018benchmarking}.

Unless the text says otherwise, the measurements come from Oracle Cloud virtual machines on a
private network. One runs both brokers: \kafka{}~4.1.1 as a single node with one partition and
one replica, so that \texttt{acks=all} is the leader's own append, and \redis{}~7 Streams, read
through a consumer group. Another, the \emph{client machine}, runs the producer and the consumer as
separate CPython processes through the kafka-python and redis-py client libraries (versions,
where recorded, in Supplement~S1), and both read one clock, so nothing here depends on synchronizing clocks. In a
control the brokers ran on the client machine itself (Supplement~S1). Its
kernel is Linux~6.8, whose scheduler is EEVDF (Earliest Eligible Virtual Deadline
First)~\cite{stoica1996proportional}.

The producer replays StatsBomb's open football event
data~\cite{statsbomb2023}; only its message sizes and rates matter here.
Each message is a JSON record of an event's identifiers and timestamps,
$\workloadBytesLo$--$\workloadBytesHi$ bytes, which one experiment pads by up to
$\workloadPadMaxKB$~KB. In nine runs out of ten a producer publishes
$\workloadRateLo$--$\workloadRateHi$ messages a second, as a sparse event feed does, and up to
$\workloadFeedsMax$ producers run at once. \emph{Utilization}\label{def:rho} $\rho$ is the fraction
of processor time busy on the client machine over a run, set by the background load, which runs
only there.

\label{def:vocabulary}A \emph{condition} is one point of the experimental design: a broker, a publish rate, a message size,
a background load and how often the consumer confirms what it has read. A \emph{run} executes a
condition once, a \emph{replicate} is a further run of it, and a \emph{campaign} is a set of runs
designed together. Where an experiment changes one variable and holds the rest, each value it gives
that variable is a \emph{configuration}. A later campaign ran on three pairs of Microsoft Azure
machines, two x86 and one Neoverse~N2, with the same brokers and clients
(\texttt{kafka-python}~2.3.2, \texttt{redis-py}~7.4.1) and \kafka{}'s Java client,
\texttt{kafka-clients}~3.9.0. It was \emph{registered}: its predictions were committed to the project's
public repository before the runs that test them~\cite{nosek2018preregistration}
(Supplement~S6.1). Supplement~S1.4 lists the runs behind each number.


\section{The Distribution of $S$}
\label{sec:finding}

On a broker that acknowledges first, $S$ is ideally a small positive margin
(Section~\ref{sec:proxy}). Measured, it is spread over
milliseconds, and part of it falls below zero (Fig.~\ref{fig:twoways}). Over the $\spanEvents$
messages of the $\spanRuns$ cloud runs that produced matched records, $\spanNegAck$ values of $S$,
$\spanNegAckPct\%$, fall below zero (excluding $\backlogLate$ messages delayed by a testbed fault;
Supplement~S1.5). We call this share the \emph{negative-span rate}. It pools runs at every load,
each weighted by its messages. Per run it goes from zero, in $\spanRunsNoNegative$ runs, to
$\spanRunRateMaxPct\%$, with a median of $\spanRunRateMedianPct\%$. It rises with utilization and
falls at real-time priority (Fig.~\ref{fig:twoways}b). Both brokers show it, \kafka{}
on $\spanKafkaNegAckPct\%$ of its $\spanKafkaEvents$ messages and \redis{} on
$\spanRedisNegAckPct\%$ of its $\spanRedisEvents$, with per-run medians of
$\spanKafkaRunRateMedianPct\%$ and $\spanRedisRunRateMedianPct\%$. The registered campaign found it
again in \kafka{}'s own Java client, at a third to
a quarter of Python's rate, and on Neoverse~N2 as on x86 (Supplement~S6.2).

\section{The Mechanism and Its Laws}
\label{sec:mechanism}

A thread must wait for a core before it can read the clock. That wait is its \emph{scheduling
delay}\label{def:scheddelay}, the time a thread that is ready to run spends queued before a core
runs it, which real-time Linux measures as scheduling latency~\cite{bristot2025timerlat}. We show,
by the kernel's timestamps and by \emph{manipulation}, moving one variable with the rest held
fixed, when this wait puts $S$ below zero and when the broker's own order does. We then state the
laws that govern how often, and on what timescale.

\subsection{When $S$ falls below zero}
\label{sec:proxy}
\label{sec:model}
$D$ and $A$ are causal chains. Each starts at the publish call, which precedes the broker's
write, which precedes both the acknowledgment and the delivery. $S$ is not a chain: its two
readings are two branches of one cause, the write, and neither has to come first. Since
Equation~\ref{eq:model} holds for every message, whatever the signs,
\begin{equation}
S < 0 \quad\text{if and only if}\quad A > D .
\label{eq:negspan}
\end{equation}
If neither thread waited, $S$ would equal the \emph{margin}\label{def:margin} $m$, the time the
message still needs to reach the consumer once the acknowledgment has reached the producer.
Each reading is late by its thread's delay, which holds any wait for a core
(Fig.~\ref{fig:model}b), so $S$ falls below zero when the acknowledging thread's delay,
$\delta_{\mathrm{ack}}$, exceeds the margin plus the consumer's own delay,
$\delta_{\mathrm{recv}}$. We measured the margin as the \emph{kernel-timed order}
$S_k = t_{\mathrm{rx}} - t_{\mathrm{rx,ack}}$, between the kernel's receive timestamps of the
message and of its acknowledgment, which no thread's delay enters. On \kafka{} the acknowledgment
came first, by a median of $\osKafkaMarginLoUs$--$\osKafkaMarginHiUs\,\mu$s, and $S_k$ fell below
zero for under 1\% of messages in $\osKafkaSkUnderOneRuns$ of $\osKafkaRuns$ runs. Under load,
$\osKafkaLatePct\%$ of the values of $S$ below zero had $S_k \geq 0$, so they are late readings. In
$\osRedisFirstRuns$ of \redis{}'s $\osRedisRuns$ runs with sixteen publish workers the delivery came
first, by
$\osRedisLeadLoUs$--$\osRedisLeadHiUs\,\mu$s at the median. \redis{}'s margin was then below zero, and a
value of $S$ below zero needed no wait. For $\osRedisOrderLoPct$--$\osRedisOrderHiPct\%$ of its
values below zero the delivery had come first (Supplement~S3.11).


\subsection{How often, and what moves the rate}
\label{sec:twostate}
\label{sec:mixture}
Each thread that reads the clock is either running, in which case its reading is late by a narrow
jitter, or waiting for a core. On \kafka{}, from an idle host to the heaviest load before its
processors are fully busy, the negative-span rate grows $\invGrowth\times$ but the jitter's width
only $\coreGrowth\times$, so load mostly changes how often the thread is waiting. Write $p$ for that
probability, the thread's \emph{waiting probability}\label{def:occupancy}, and $G$ for the chance
that the rest of its wait, the \emph{residual wait}, outlasts a given time. To leading order,
if the consumer's own wait is short,
\begin{equation}
\Pr\bigl[\,S<0 \mid m\,\bigr] \;\approx\; p\,G(m) ,
\label{eq:occupancy}
\end{equation}
the waiting probability times the chance that a residual wait outlasts the margin: the textbook
decomposition of a wait, here read from the order of two clock readings. Load, its placement and priority
move $p$; the path's length moves $m$.

\textbf{Priority.} Real-time priority for the threads that read the clock should cut their
waiting probability while utilization stays fixed. Every manipulation ran both brokers, $25$ runs
a configuration on each (Table~\ref{tab:mechanism}). Across \rtPairsWord{} matched pairs from
$\rtRhoLow$ to $\rtRhoHigh\%$ utilization, real-time priority cut the rate $\rtFactorLow$- to
$\rtFactorHigh$-fold on \kafka{} and $\rtRedisFactorLow$- to $\rtRedisFactorHigh$-fold on
\redis{}, and at least $\rtKafkaLowerBound$- and $\rtRedisLowerBound$-fold in every pair, the
smallest of the pairs' run-level lower bounds. Achieved utilization matched to within
$\manipWorst$ (Supplement~S3.1). That refutes any account in which utilization alone sets the
rate, including the queueing form we had ourselves adopted. In the registered campaign, on other
machines, real-time priority removed the values below zero on \kafka{} in every run, and load
raised the rate in all five \kafka{} campaigns that tested it (Supplement~S6.2).

\textbf{Placement.} With the background load concentrated on six of the \testbedCpusWord{} cores
or spread over all of them, two configurations reached the same utilization, $\rho =
\mechGeomRho$, and on both brokers they gave different rates (Supplement~S3.2). On \kafka{} the
spread load gave the higher rate, $\GeomOrigFactor$-fold [bootstrap over runs, $95\%$: $\placeKafkaOrigCI$], and

Spreading the load leaves no core free, so a woken thread waits more often. On \redis{} it was the concentrated
load that gave more values below zero, so where the load is placed matters on both brokers, in
opposite directions.

\textbf{Path length.} A wait of a given size overlaps a short path almost entirely and a long one
hardly at all. Padding the payload lengthens the time to the consumer's reading, by transfer and
parsing, at nearly unchanged utilization. On \kafka{} it raised the median of $S$

$G$ predicts, and the opposite of what stress on the host would cause (Supplement~S3.3).

\subsection{The timescale the slice sets}
\label{sec:tail}
A thread woken while another holds the core waits out what is left of the running
thread's \emph{slice}, the time the scheduler lets a thread run at a turn. It can wait up to a whole slice,
because the scheduler does not preempt the running thread for it before that slice is spent.
The kernel checks for a spent slice only at each \emph{tick} $h$ of its timer,
$\tickMs$~ms on our Oracle hosts, so the wait can run up to a tick past the slice. The kernel sets
the base slice $s$ from the CPU count $n$, with a cap:
\begin{equation}
s \;=\; s_0\times\bigl(1+\lfloor\log_2\min(n,8)\rfloor\bigr),
\label{eq:slice}
\end{equation}
where $s_0$ is $0.75$~ms in Linux~6.8 and $\sliceConstantMs$~ms after a 2025
change~\cite{zhou2025slice} that Ubuntu backported to the Linux~6.8 kernels we ran (Supplement~S3.7).
That gives
$\sliceFactor \times \sliceConstantMs$~ms $= \baseSliceMs$~ms on our hosts'
\testbedCpusWord{} CPUs. The traced waits carry that timescale: the last of their
\tracedModesWord{} local maxima, which survive a $\stallCoarsenFactor\times$ widening of the
buckets, sits in the $\tracedModeLo$--$\tracedModeHi$~ms bucket that contains the slice, with
$\tracedModeShare\%$ of all wakeups, and above it the counts collapse (Supplement~S3.7). The trace
also counts waits that begin when a
thread is preempted, which last about a whole slice. The thread that reads the acknowledgment is
instead woken by the reply. Its own wait, timed in the registered campaign and read after the
predictions were judged, is the rest of a slice (Fig.~\ref{fig:residual}).

The CPU count moves the slice. In the registered campaign the slice read back at 2, 4 and 8 CPUs as
Equation~\ref{eq:slice} gives with $s_0 = \sliceConstantMs$~ms. The law puts the halfway point of
the rate's fall inside $[s, s + h]$, from the slice to a tick past it. On \kafka{} the rate fell
inside that band at 8 CPUs, the one count whose slice reaches its shortest end-to-end latency. On
\redis{} a free reading, a curve required only never to rise, placed the fall there at all
three counts. With the slice set by hand, that curve did so at every slice on both brokers, with
slopes on $s$ of $\lawFreeSlopeKafka$ on \kafka{} and $\lawFreeSlopeRedis$ on
\redis{}; Section~\ref{sec:threats} gives the registered verdicts (Supplement~S6.2).

A whole slice is $\sliceOverDeliveryLo$--$\sliceOverDeliveryHi$ times the per-condition median
end-to-end latencies we measured, $\condDeliveryLoMs$--$\condDeliveryHiMs$~ms, so the slice lands on
the scale of the paths now benchmarked. Together, Equations~\ref{eq:negspan}--\ref{eq:slice} say
that the rate rises with the waiting probability and falls as the margin outgrows the residual
wait, whose scale the slice sets. On our kernel any host with at least as many CPUs as ours has a slice of
$\baseSliceMs$~ms, so a single wait can outlast any margin shorter than that.

\subsection{Tools run}
\label{sec:toolsrun}
Reading a tool shows what it does with a value below zero, not whether it ever meets one. We
therefore ran \toolsRunWord{} benchmarking tools, \toolsRoundsWord{} rounds each, in blocks whose
predictions were fixed from the tools' sources and made public before their runs
(Supplement~S5). Four tests followed. First, a delay was added to the
path in steps. Of the tools the delay could reach, all but two
reported a latency that rose $\toolsSlopeLo$--$\toolsSlopeHi$~ms for each millisecond added, each
time the path crossed the delay, so those tools measure the path. Second, the clock of the process that subtracts was set back, by two
offsets longer than the interval the tool times. The figures of the \toolsOneClockWord{} one-clock tools stayed
within a quarter of the offset in $\toolsOneClockHeld$ of their $\toolsOneClockOf$ runs. All of
them but PerfKit Benchmarker, whose two processes
share one machine, take both timestamps in one process, where no clock offset can reach them.

one-process tools mostly time
something other than a delivery: \toolsOneProcessTripWord{} a round trip and
\toolsOneProcessAckWord{} the acknowledgment alone. The rest time publish to receipt, but in one
process, so they cannot see a separate receiving process's wait for a core. Another \toolsTwoClockWord{} timestamp a message in one process and subtract in
another, and in $\toolsTwoClockRuns$ of their $\toolsTwoClockOf$ runs the moved clock shifted their

makes such a value some $10^{19}$~ms.

\subsection{A positivity filter on a millisecond clock}
\label{sec:extmethod}
\label{sec:extphase}
\label{sec:extcomp}
The positivity filter is one of the cuts above, and the one that deletes more than the
values below zero. In statistical
terms it truncates the distribution at zero: what it removes is not counted, as it would be if
censored. We measured it in
depth in a broker benchmark whose end-to-end percentiles $\reachReports$ public reports print, the
OpenMessaging
Benchmark~\cite{openmessaging2018}. Its filter was added in 2018 because its end-to-end latency
``is calculated based on time difference of \texttt{System.currentTimeMillis()} on two different
machines'' and ``can be negative''~\cite{openmessaging_pr56}, and its histogram rejects values
below zero outright. For clocks that disagree, the filter is a sound local fix.

It has two side effects. Its clock counts whole milliseconds (whole seconds in its RabbitMQ driver;
Supplement~S5), so its \emph{timestamp resolution}
$\tau$, the smallest step a timestamp can take, is a millisecond. A message that arrives before
the millisecond digit changes therefore computes to zero and is deleted (Fig.~\ref{fig:deletion}a).
And nothing counts what the filter deletes. A sample survives only if a millisecond boundary falls between its two timestamps. With publish instants placed uniformly within the millisecond, that happens with
probability $T_{\mathrm{true}}/\tau$ on a path shorter than $\tau$, where
$T_{\mathrm{true}}$\label{def:ttrue}, the \emph{true end-to-end latency}, is the one a perfect
clock read without delay would give. So the share of samples kept, the \emph{retention}, is
\begin{equation}
\label{eq:retention}
\text{retention} \;=\; \min\!\left(1,\; \frac{T_{\mathrm{true}}}{\tau}\right) .
\end{equation}
Every sample kept on such a path reads exactly one step, so two brokers whose messages all
arrive within a millisecond print the same median and differ only in their retention, which is
never printed. The arithmetic is in Hewlett-Packard's 1970 counter note~\cite{hp1970tia}, but the
deletion is not: that counter keeps its zero readings.

We added counters that record, by sign, every sample the filter discards, and changed nothing
else. Every run used the benchmark's embedded mode, which runs it whole in one Java virtual
machine. Of the $\ombMedianCells$ settings whose own summary we captured,
$\ombGridMedianCells$ printed a median of exactly $\ombGridPrintedLo$ or $\ombGridPrintedHi$~ms,
computed from $\ombGridRetentionMin$--$\ombGridRetentionMax\%$ of the samples
(Fig.~\ref{fig:deletion}b). Two
replicates of one setting kept $\ombKeptLo$ and $\ombKeptHi$ samples, $\ombRetentionFold$-fold
apart, and printed the same median. The filter can also inflate a median. At
$\ombAboveGridPartialKB$~KB, the \ombAboveGridPartialWord{} settings kept only
$\ombAboveGridPartialRetLo$--$\ombAboveGridPartialRetHi\%$ of samples, since most computed to
zero, yet printed the slow remainder's medians, $\ombAboveGridPartialMedLo$ and
$\ombAboveGridPartialMedHi$~ms.

Equation~\ref{eq:retention} holds where it can be tested. It predicts one retention for every
configuration whose publish interval bears no ratio of small whole numbers to $\tau$, an
\emph{incommensurate} rate. The \spreadIncommensurateWord{} such configurations all keep
$\spreadIncommensurateLo$--$\spreadIncommensurateHi\%$ at the median. That puts $T_{\mathrm{true}}$ at
$\spreadIncommensurateTrueMs$~ms, read as a mean over messages with any path longer than $\tau$
counted as $\tau$. Where the ratio is one of small whole numbers, the schedule phase-locks
with the clock, and retention takes few values; a registered change of message size
moved a configuration onto one and off it (Supplement~S4.3).

Counted by sign, the filter hides two failures. On \kafka{} the $\ombKafkaDiscarded$ samples it
discarded over $\ombKafkaRuns$ runs hold $\ombKafkaNegatives$ values below zero; each of those samples
computed to zero, lost to the clock's step. On \redis{}, where the benchmark subtracts the broker's millisecond timestamp from the
consumer's clock, all $\ombRedisNegatives$ values below zero in $\ombRedisRuns$ runs were exactly
$-\tau$, the mark of two floored clocks less than a millisecond apart (Supplement~S4.4).

\textbf{Public reports.}\label{sec:reports} An audit of the benchmark's public reports, registered
before we read any, looked for the deletion's signature, a printed end-to-end median of exactly
1~ms. Of the $\reachMedianConfigs$ end-to-end medians in $\reachReports$ reports,
\reachPrimaryConfigsWord{} carry it, in \reachPrimaryReportsWord{} reports, and no report states how
many samples it kept. The signature is rare partly because $\reachFinerReports$ reports come from
copies with a finer clock (Supplement~S5).

\textbf{Let the kernel timestamp each message.}\label{sec:fix} A tool reads each of a message's
timestamps in one of its threads, which may first wait for a core. The kernel timestamps
each packet as it leaves and enters a machine, the transmit and receive timestamps,
without waiting for any program's thread. A latency timed from a message's transmit timestamp to
its receive timestamp, the \emph{kernel-timed latency} $W$, therefore holds the network and the
broker but no client thread's wait, whenever each socket read drains one packet and a consumer
request already waits at the broker. No wait is lost:
$H_{\mathrm{out}}$ runs from the publish call to the transmit timestamp and $H_{\mathrm{in}}$ runs
from the receive timestamp to the consumer's reading, so
$D = H_{\mathrm{out}} + W + H_{\mathrm{in}}$ for every message (Fig.~\ref{fig:kernel}). This
is network measurement's rule: delay is defined between times on the wire, not
the host times a program reads~\cite{rfc2330}, and the one-way delay standard bounds each host's
share by terms that $H_{\mathrm{out}}$ and $H_{\mathrm{in}}$ measure~\cite{rfc7679}.

All five predictions, fixed before any run, held. Over $\fullFixRuns$ runs on both brokers, timed
from packet captures, the median of $W$ moved at most $\fullFixMedianMovePct\%$ and its 99th
percentile $\fullFixTailMovePct\%$ across load (none or $\fullFixLoadPct\%$) and priority,
inside the bands fixed before the runs, $\fullFixMedianMarginPct\%$ and $\fullFixTailMarginPct\%$.
With six runs a setup, the run-level intervals on those moves reach $\fixCaptureMedianCIHiPct\%$
and $\fixCaptureTailCIHiPct\%$, so the bands hold for the point estimates, not their intervals
(Supplement~S3.9). In the same runs, load at normal priority raised the 99th percentile of $D$
$\fullFixTailRatioLo$--$\fullFixTailRatioHi$-fold. A delay added between broker and consumer
raised $W$ $\osSlopeWLo$--$\osSlopeWHi$~ms per millisecond (Supplement~S3.11), and $W$ never
reached zero, so a positivity filter deletes nothing.

\textbf{Read those timestamps on the tool's own sockets.} A tool need not capture packets. On
Linux it reads these timestamps through the \texttt{SO\_TIMESTAMPING} \emph{socket option},
a setting a program makes on a socket, in four steps~\cite{linux_timestamping}.
\begin{enumerate}
\item On each connection to the broker, before its first write, turn on the kernel's software
timestamps for transmit and receive, with an identifier for each write counted in bytes
(\texttt{OPT\_ID} with \texttt{OPT\_ID\_TCP}).
\item The kernel leaves each write's transmit timestamp on the socket's \emph{error queue}, keyed by
the byte offset of the write's last byte; writes coalesced into one packet share one timestamp.
Read the error queue at every write and read, since while it holds a timestamp a client that polls
the socket spins.
\item Take the receive timestamp the kernel returns with each read, that of the last packet the
read consumed.
\item Find each message in the bytes by an identifier the benchmark puts in each payload; this
needs a connection without compression or encryption. Time it from the transmit timestamp of the write
that carried it to the receive timestamp of the read that delivered it. Report that latency beside
$D$, and count any message left without a timestamp.
\end{enumerate}
Lancet reads a request-reply service's timestamps this way~\cite{kogias2019lancet}, Fathom
splits a fleet's call latency into host and network parts with kernel
instrumentation~\cite{qureshi2023fathom}, and Zuo et al.\ split a host's network-stack latency at
kernel timestamps~\cite{zuo2026hoststack}. We read these timestamps beneath unmodified broker
clients, on the one-way path from producer to consumer. Our Python module takes these steps for
both brokers (\brk{scripts/so_timestamps.py}). In $\soFixRuns$ more runs it came
within $\soFixAgreeMedianHiUs\,\mu$s of the captures' latency at the median. Both read the kernel's
receive timestamp, so this shows the module matches timestamps to messages. The network
card's own timestamps, $\fullFixKernelDelayLoUs$--$\fullFixKernelDelayHiUs\,\mu$s earlier at the
median, bound how far the kernel's timestamps lie from the wire (Supplement~S3.9). Under load at
normal priority the tail of $D$ again grew $\soFixTailRatioLo$--$\soFixTailRatioHi$-fold while the
latency the module timed held level, its median moving at most $\soFixMedianMovePct\%$ across load
and priority, with run-level intervals reaching $\fixSocketMedianCIHiPct\%$
(Fig.~\ref{fig:fixbenefit}). Against the
capture runs, taking the timestamps moved the clients' own time, $D - W$, by $\moduleCostKafkaLo$ to
$\moduleCostKafkaHi\,\mu$s on \kafka{} and $\moduleCostRedisLo$ to $\moduleCostRedisHi\,\mu$s on
\redis{}, and the 99th percentile of $D$ by $\moduleTailLo$ to $\moduleTailHi\,\mu$s, the drift
between two days included (Supplement~S3.10). Up to $\osTopRate$ messages a second the sockets
agreed with the captures within $\osLadderAgreeHiUs\,\mu$s (Supplement~S3.11).

\textbf{What a tool must handle.} A read that drains several packets times the earlier ones late,
by their wait in the socket, which is the consumer's wait. A pull consumer, which asks the broker
for each batch as \kafka{}'s and \redis{}'s do, adds another: a message the broker stores while no
request is outstanding waits for the next one, which the consumer's thread issues after its own
wait, inside $W$. A tool can flag such messages, those delivered in answer to a request whose
transmit timestamp follows the message's own; Supplement~S3.11 counts them at each rate. Where
receive processing runs
in a kernel thread, under threaded network polling or when an overloaded softirq moves to
\texttt{ksoftirqd}, the receive timestamp waits for a core too. Reading a card's hardware timestamp
avoids that wait, on a clock of its own that the tool must tie to the system's. Where a driver
gives no software transmit timestamp, as on our cloud's accelerated network, ask for the one
taken before the packet scheduler (\texttt{TX\_SCHED}); any queueing there then falls inside $W$.
Our virtual driver claims software timestamps it does not give (Supplement~S3.10), so check which
timestamps arrive. With producer
and consumer on two machines, $W$ spans two clocks and includes their offset, so they must be
synchronized well below the latency. A design in which the consumer acknowledges back to the
producer times two legs on one clock, not the one leg wanted. Recovering the two clocks' offset
from logs instead is itself synchronization. Java's standard sockets expose neither the option nor the
error queue, so a Java tool needs a native call, through the Java Native Interface or the
foreign-function interface. On Linux~6.15 and later an eBPF program can replace the native call
for transmit timestamps, not for receive timestamps. A kernel-bypass stack
has no kernel timestamps at all. A tool that cannot yet take them needs what follows.

\textbf{Sign-check every run.}\label{sec:gate}\label{sec:audit} The \emph{sign check} rejects a
run when more than one percent of its messages carry a value below zero in any latency component it
records ($S$, the publish delay or the processing-time latency), or when the median of any of them
is below zero. It rejected $\auditRejectedCloud$ of the $\auditRunsCloud$ cloud runs behind our
results ($\auditPctCloud\%$; Supplement~S2). It sees only the worst cases: the publish latency
exceeds half the end-to-end latency on $\diseaseOverHalf\%$ of messages, but the check is triggered
only by the $\diseaseOverWhole\%$ on which it exceeds the whole, and a latency that load inflates
but leaves positive passes the check by construction. The check also assumes a broker that acknowledges no
later than it delivers. On one that delivers first, as \redis{} often does, a value of $S$ below
zero needs no wait, so there it should read the publish-timed spans alone. The check therefore needs the
repair that follows.

\textbf{Time from the publish call, or add the publish latency back.}\label{sec:cost}
The repair is Equation~\ref{eq:model}: $D = S + A$ for every message, and $A$ is read on the producer's side of
the same clock, so a benchmark that records its publish latency recovers each message's end-to-end
latency exactly. Error arises only where a benchmark keeps summaries. Over groups of runs,
the median of $S$ plus the median of $A$ misses the median of $D$ by a median of
$\recoveryErrKafka\%$ on \kafka{}'s $\recoveryKafkaN$ groups and $\recoveryErrRedis\%$ on \redis{}'s
$\recoveryRedisN$, and by $\recoveryErrKafkaHi$ and $\recoveryErrRedisHi\%$ at the upper quartile
(Supplement~S2.1). On each
broker, no difference is detectable between the groups of runs the sign check passes and those it
rejects.
The publish latency does not grow as leg~2 lengthens. On one path, the relative error of $S$ as a latency, $A/D$, therefore falls
as $1/D$. At our median publish latency, $A = \ackLagMedianUs\,\mu$s, it is
$\exposureErrOne\%$ at an end-to-end latency of 1~ms and $\exposureErrTen\%$ at 10~ms, where
the tenth to ninetieth percentiles of $A$ give $\exposureErrTenLo$--$\exposureErrTenHi\%$.
Below $D = \exposureCrossover$~ms, or $\exposureCrossoverHi$~ms at the ninetieth percentile of $A$,
the publish latency exceeds $D$ itself. From one
condition to the next, though, \kafka{}'s $A$ grows with $D$, so all its groups lie above that
curve, while \redis{}'s straddle it (Supplement~S2.1 draws both). Over \kafka{}'s
$\exposureKafkaGroups$ groups $S$ understates $D$ $\understateKafkaFactor\times$ at the median
(interquartile range $\understateKafkaIQRLo$--$\understateKafkaIQRHi\times$), and over \redis{}'s
$\exposureRedisGroups$, $\understateRedisFactor\times$
($\understateRedisIQRLo$--$\understateRedisIQRHi\times$), and over $\gapDistortionPairs$ matched
workloads it inflates the gap between the brokers $\gapDistortionPaired\times$ at the median
(Supplement~S2.1). Timing from the publish call removes
the values below zero, but not the consumer's own wait for a core, which lengthens every latency,
unseen by any check. In $\recvWaitRuns$ runs it added
$\recvWaitAddedLo$--$\recvWaitAddedHi$~ms to the mean of $D$, while the receiving
thread's median wait was $\recvWaitMedianLoUs$--$\recvWaitMedianHiUs\,\mu$s (Supplement~S3.8), a
wait the kernel-timed latency excludes.

\textbf{Give the threads that read the clock a core.} Real-time priority cut the negative-span rate
at least $\rtKafkaLowerBound$-fold on \kafka{} and $\rtRedisLowerBound$-fold on \redis{} in every
pair, at unchanged background load (Table~\ref{tab:mechanism}). A busy-polling thread, spinning on
a core of its own, never waits to be woken and should buy the same for the price of that core,
though we did not measure it. Since Linux~6.12 a thread can instead ask for a
shorter slice of its own, to run sooner when woken~\cite{zijlstra2024slice}, which our
Linux~6.8 kernels lack. At real-time priority the rate settles
at $\rtResidualMinPct$--$\rtResidualMaxPct\%$ on \kafka{} and
$\rtRedisResidualMinPct$--$\rtRedisResidualMaxPct\%$ on \redis{} (Supplement~S3.1), so the sign
check stays. A real-time or polling thread also changes the system it measures.

A better-synchronized clock repairs neither the late reading nor the deletion: the values of $S$
below zero arise on one clock, and the deletion from the clock's step. A finer clock confines the
deletion to faster paths but leaves the filter and every value of $S$ below zero in place. The
remedies are therefore ordered: record at native resolution, count what is discarded and randomize
the publish instants, and only then improve the clocks' synchronization.


\section{Related Work}
\label{sec:related}

\textbf{Scheduling delay.} That a ready thread can wait for a core is well
known~\cite{gregg2016runqlat}. Behind another thread's slice the wait adds milliseconds to a
server's tail latency, and real-time priority removes that wait~\cite{li2014tales}. Co-located
work lengthens it~\cite{leverich2014reconciling}, a longer slice extends it~\cite{jia2024skyloft},
and real-time Linux measures it as noise~\cite{bristot2023osnoise}. In Linux's network stack a reader's wait
from its wakeup by arriving data to its running is the main source of tail
latency~\cite{zuo2026hoststack}, and the limits of the timers that benchmarks read are known
too~\cite{kuperberg2011timers}. Load testers of microsecond-scale services correct for the
\emph{client bias} their own queueing and scheduling add~\cite{zhang2016treadmill,kogias2019lancet}. Villain et al.\ found that an
outgoing socket timestamp ``does not respect causality'' under every stress pattern, including
none~\cite{villain2012probing}. None gives the
consequence for a difference read by two processes: that it falls below zero at a rate set by the
waiting probability and the margin, on the timescale of the slice.

\textbf{Clocks.} Across hosts, values below zero are read as clocks that disagree, and on one host as
a thread preempted after it read the clock~\cite{mckenney2023perfbook}, but neither reading measures
the rate or its laws. Sharma et al.\ read negative timing spans as clock skew, since ``queueing
alone cannot produce negative timing spans''~\cite{sharma2026causality}. For the backlog they
model we agree, but a timestamping thread waits in a second queue, the kernel's run queue. Van Dongen and Van den Poel, seeing latencies
below zero on up to a tenth of their events, took both timestamps from one
broker~\cite{vandongen2020evaluation}, the one-clock rule reached by another route. Network measurement defines delay between wire
times~\cite{rfc7679}, and Lancet and Fathom read such times through the
kernel~\cite{kogias2019lancet,qureshi2023fathom}. We read them beneath unmodified broker clients.

\textbf{Resolution and discarded samples.} The retention arithmetic and its cure, phase jitter,
are in a 1970 counter note~\cite{hp1970tia}, and a clock coarser than the intervals it times can
still estimate their mean~\cite{danzig1990highres}. IP
measurement advises randomizing probe times~\cite{rfc2330,baccelli2006pasta}, since a periodic schedule can
synchronize with periodic behavior~\cite{rfc3432}, here the clock's step. Coordinated
omission~\cite{tene2015latency} is the deletion's mirror image: it fails to record samples that
would have been slow. Network measurement reports the share of traces it rejects~\cite{paxson1998calibrating}
and keeps a packet timestamped in the future~\cite{rfc4656}, and rigorous benchmark reporting asks
that removed outliers be counted~\cite{georges2007rigorous,hoefler2015benchmarking}. The tools we
audited remove samples before any analyst sees them and count none, a case that neither that
literature nor the principles for reproducible performance evaluation in the
cloud~\cite{papadopoulos2021methodological} address. Stream-processing benchmarks compute latency
from \kafka{}'s millisecond timestamps of a record and of its result~\cite{henning2024shufflebench},
so the retention arithmetic applies wherever their latencies fall below a millisecond. We add these
checks, applied where a benchmark reports a latency.


\section{Limitations}
\label{sec:threats}
\label{sec:limitations}

That scheduling makes \kafka{}'s readings late is now observed message by message
(Section~\ref{sec:twostate}). One clock excludes clock skew, and the manipulations exclude
utilization and stress. Real-time priority excludes the interrupt noise that reaches every
scheduling class, while timer slack, which differs between classes, cannot delay a wakeup on
arriving data. Clocks that disagree across virtual CPUs are excluded too. On the Oracle machines a
clock whose read costs at most $\clockIncrementNs$~ns can only be one the kernel uses where the
CPUs' clocks agree. The Azure machines read the processor's timestamp counter, which the kernel uses as its
clock only where the counters agree (Supplement~S3.6). Since $D$ never fell below zero, no offset can
exceed its smallest value, $\spanOffsetMargin$ times smaller than the deepest value of $S$. Both
testbeds are virtual, so \emph{steal time},
the time a virtual processor is
ready but waits while the hypervisor runs another machine, is bounded, not excluded: real-time
priority, a setting inside our virtual machine, cannot shorten it, yet it cut the rate.
The rival we had left open, a broker that delivers before it acknowledges, is real on
\redis{} and rare on \kafka{} (Section~\ref{sec:proxy}). By our registered rule, \redis{}'s values
of $S$ below zero with the delivery first count as its reply order, though the readings' delays
still decide which delivery-first messages fall below zero. That order lets \redis{}'s real-time
rate stay above zero: across the matched pairs it barely
moved with load, $\rtRedisFloorLightLoadPct\%$ at the
lower loads and $\rtRedisFloorHeavyLoadPct\%$ at the higher, while the normal-priority rate rose
from $\rtRedisNormalLightLoadPct\%$ to $\rtRedisNormalHeavyLoadPct\%$ (Supplement~S3.1). Our CPython timestamps also
wait on the interpreter lock, and \kafka{}'s Java client, which has none, shows values below zero
too, at a third to a quarter of Python's rate (Supplement~S6.2), so the effect needs no lock. With
one publish worker instead of sixteen, \redis{}'s real-time rate fell from $\osGilIdleSixteenPct\%$ to
$\osGilIdleOnePct\%$ with no load, so there the lock the workers share sets most of it, though not
under load (Supplement~S3.11). We have not tested why placement moves the two brokers' rates in
opposite directions, nor traced the cause of \redis{}'s mode near $-\osBumpMidUs\,\mu$s in
Fig.~\ref{fig:twoways}; on a second pair, a processor waking from idle did not cause it
(Supplement~S3.11).

Equation~\ref{eq:occupancy} describes how the rate moves between conditions. Inside one, the rate
rises with $D$ in $\rbdUp$ of $\rbdTestable$ testable conditions, because a long delivery comes
with a long publish latency (Supplement~S3.4). A registered prediction that
priority would cut the waiting probability at least tenfold failed: by the scheduler's counters,
which average away the tail, it fell $\eaSevenOccFallLo$- to $\eaSevenOccFallHi$-fold, so the
equation's factorization is untested between conditions. In the registered campaign, none of three predictions of the rate from recorded waits
held within the registered factor of $1.5$ on every pair and broker. Predictions from every thread's waits gave
$\pSixRatioLo$--$\pSixRatioHi$ times the measured rate. The share of readings below zero whose
thread had mostly been waiting reached the registered $90\%$ on \recMostlyWaitingHoldsWord{} of
\recMostlyWaitingPartsWord{} combinations. The law's fitted shape placed the fall in the slice's
band less often than the free reading, and at no CPU count on \redis{}. Neither prediction of
where the rate falls at a hand-set slice passed both readings, and those of how quickly it falls
held on one broker at most (Supplement~S6.2). Nor, with the
kernel-timed margin, did the rate fall from each fifth of the margin to the next, as registered.
Turning off the scheduler's run-to-parity rule, which lets a running thread keep its core until its
slice is spent, moved neither the rate nor the acknowledging thread's delay, against a registered
cut to two-thirds, so the rule alone does not hold a woken thread off the core
(Supplement~S3.11). The kernel trace pools both
brokers' threads and is not free: under it \kafka{}'s
real-time runs read no value below zero, against $\untracedRtNegatives$ in $\untracedRtEvents$
untraced. The traced real-time configurations therefore cannot test the trace check, though
under the trace the normal-priority rate did not move (Supplement~S3.5). The
registered campaign's recording raised the rate it recorded $\recRaisedLo$- to $\recRaisedHi$-fold,
so each prediction is held against its run's own rate. The base slice on the Oracle
hosts is derived, not read off them; the Azure hosts read it back. The constants are those of one
EEVDF-era kernel, before Linux~6.17 limited the run-to-parity rule, a change for threads that set
their own slices. The distribution and the laws
were
measured with paced producers at about one message a second each, and fifty messages a second in
the registered campaign, where the threads that read the clock sleep between messages and must be
woken. At $\osMidRate$ messages a second on an idle host, \osMidSplitRunsWord{} of
\osMidRunsWord{} runs had most values of $S$ below zero for the whole run. The laws were not tested
above fifty messages a second (Supplement~S3.11). The rule that leaves out messages delayed by a testbed fault
was chosen
after the Oracle testbed was gone (Supplement~S1.5).

The fix was tested from packet captures and, through a Python module, on the clients' own sockets.
Those tests used one pair of machines and one kernel, with one partition, background load on the
client machine alone, and the producer and the consumer on one machine. Its stillness under load
was judged at fifty messages a second only. On a second pair, under load,
\kafka{}'s kernel-timed latency held within $\osLadderKafkaMovePct\%$ and \redis{}'s rose
$\osLadderRedisRisePct\%$. At $\osTopRate$
messages a second, with $\osPullTopLoPct$--$\osPullTopHiPct\%$ of messages flagged,
a pull consumer's wait entered $W$. On that
virtual network a departing packet's timestamp came only from before the packet scheduler, and the
clients used neither encryption nor compression. We tested no designs that timestamp in hardware
or pin a busy-polling thread to its own core, which keep the waiting state out of the latency they
time.

The deletion is demonstrated in one benchmark, in its embedded mode, and reproduced in an
independent program of ours; the benchmark's distributed mode, run on the Azure machines, dropped
values below zero under a moved clock, uncounted (Supplement~S4.5). In the registered
change of message size
(Supplement~S4.3), the $32$~KB configuration pinned at $\flipPinThirtyTwo\%$ retention, not the
predicted $\flipVertexTwoThirds\%$. The audit found the deletion's signature in few public results,
so we claim it for those and our own runs only. We chose the tools in rounds, not by sampling,
classified the \harnessAuditedWord{} tools by reading them, and ran the \toolsRunWord{} tools on a single
kernel and machine pair, at one publish rate. How much a deployment loses depends on its end-to-end
latency and publish rate, so we recommend reporting retention rather than calling any reported
number wrong.


\section{Conclusion}
\label{sec:conclusion}

A latency benchmark measures the system only while the delay before each reading is short beside
the latency it measures. On one machine's clock, the moment a producer reads a broker's
acknowledgment and the moment a consumer reads the message can differ by milliseconds, in
either order. A thread waits for a core, for up to a
scheduler's slice, before it reads the clock, and a broker that delivers first needs no
wait. Across the industry such values are deleted, replaced or never measured, a positivity
filter on a millisecond clock deletes the fastest messages too, and no report we audited says how
many samples it kept. On Linux a tool can time each message between the kernel's timestamps, read
on its own sockets, and report that latency beside the end-to-end latency. At fifty messages a
second the kernel-timed latency held no client thread's wait. Before acting on a broker latency below a few milliseconds, ask what it
was timed from, how many samples the tool kept, and how many it discarded, by sign.
