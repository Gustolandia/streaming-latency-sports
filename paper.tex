\begin{abstract}
Engineers choose message brokers partly by benchmarks that report latencies below a millisecond. A
broker acknowledges each message to the producer and delivers it to the consumer. We timed both on
one machine's clock. Their difference spreads over milliseconds. Part of it falls below zero,
yet no message arrives before it is published. On one broker the acknowledgment arrives first,
and there the cause is scheduling. The thread that reads the acknowledgment can wait for a
processor core until the consumer has read the message. The other broker often delivers first. We
derive laws for the share below zero and test them by controlled experiments. The share rises with
processor load and falls when clock-reading threads get real-time priority. A wait for a core can
also delay the consumer's next request, so a message can wait at the broker. An industry-wide audit
finds that most tools discard such values uncounted or never measure them. Such a filter on a
millisecond clock also deletes the fastest messages. Of the audited brokers, only an emulator and one
feature marked unstable report that wait at the broker. We give a general solution for tools and
brokers, and test the tools' part.
\end{abstract}

\IEEEraisesectionheading{\section{Introduction}\label{sec:intro}}

\IEEEPARstart{M}{any} online services move their data through a message broker. A broker is a
service that passes messages between programs (Fig.~\ref{fig:model}a). The program that publishes
a message is the \emph{producer}. The program that receives it is the \emph{consumer}. Engineers
choose among brokers partly by latency benchmarks~\cite{openmessaging2018}. These benchmarks time
each message from the producer to the consumer. They now report latencies below a
millisecond~\cite{redis_streams}. At that scale, a thread's wait for a processor core can be longer
than the latency itself. So a team that ranks brokers by such a number may act on how the number
was measured, and not on the broker. The same holds for a team that promises a response time with
such a number. This paper shows how to separate the two and how to measure the broker alone.

The problem matters beyond any one benchmark. Delays of microseconds now shape how datacenter
systems are built~\cite{barroso2017killer}. A large service is only as fast as the slowest of its
many parts~\cite{dean2013tail}, so its designers need latencies that they can trust. Yet an
experiment on a computer system can produce wrong data although nothing in it looks
wrong~\cite{mytkowicz2009wrong}. Scientists in many fields share this
concern~\cite{baker2016reproducibility}. Our first benchmark timed each message from the broker's
acknowledgment. A latency timed that way understates the message's trip from the producer to the
consumer several-fold. It also distorts comparisons between brokers (Section~\ref{sec:finding}).

We study one difference. The broker writes each message to its log. Then it returns an
acknowledgment to the producer and delivers the message to the consumer. Let the producer and the
consumer run on one machine and read its one clock. The producer reads the acknowledgment at
$t_{\mathrm{ack}}$, and the consumer reads the message at $t_{\mathrm{recv}}$. On a broker that
acknowledges first, the two readings should come in that order. They should be apart only by a
small positive margin. This margin is how much later the message reaches the consumer than the
acknowledgment reaches the producer.
We make four contributions.
\begin{enumerate}
\item \textbf{The distribution} (Section~\ref{sec:finding}). On one clock,
$S = t_{\mathrm{recv}} - t_{\mathrm{ack}}$ spreads over milliseconds, and $\spanNegAckPct\%$ of its
values fall below zero. Nothing arrived early. The \emph{publish call} is the moment the producer
hands the message over. No latency timed from the publish call falls below zero.
\item \textbf{The mechanism, and its laws} (Section~\ref{sec:mechanism}). A thread must wait for a
core before it can read the clock. On \kafka{}, the kernel's timestamps show the acknowledgment
arriving first. There the thread that reads the acknowledgment can wait for a core until the
consumer has read the message. \redis{} often delivers the message first, so most of its values
below zero need no wait. The share of $S$ below zero rises with processor load and depends on
where the load runs. It falls on longer paths. Its timescale is the scheduler's slice, which the
CPU count sets. \emph{Real-time priority} runs the threads that read the clock ahead of every
thread at the default \emph{normal priority}. The \emph{background load} is the processor work that
runs beside the clients. Real-time priority cut that share at least
$\rtKafkaLowerBound$-fold on \kafka{} and $\rtRedisLowerBound$-fold on \redis{}. It did so in every
matched pair, while the background load stayed the same. The same wait can also delay the next request of a
consumer that keeps one request at a time. A message can then wait at the broker for that request.
\item \textbf{The industry-wide audit} (Section~\ref{sec:external}). We read \harnessMessageWord{}
message tools at source to see what each does with a latency at or below zero. Of these,
\harnessMessageCutAllWord{} cut such a latency out of a figure they report. All but one of them
count none of the values they cut. The one that counts them
is the Storage Benchmark Kit (SBK). Under the strictest reading of our classification,
\auditStrictWord{} still cut them. Of the \toolsRunWord{} tools we ran, \toolsOneProcessWord{} take
both timestamps in one process, where no clock offset can reach them. But \toolsOneProcessTripWord{}
of those time a round trip and \toolsOneProcessAckWord{} only the acknowledgment. Neither is a
delivery's \emph{one-way delay}~\cite{rfc7679}. A one-way delay is the time from the sender to the
receiver. The rest cannot see the wait of a separate receiving process. On a millisecond clock, a
filter that keeps only latencies above zero also deletes the fastest messages. No public report we
audited says how many samples such a filter kept. The brokers that the industry's tools time report
at most when a message arrived, or its whole time at the broker in milliseconds.
\item \textbf{What to do} (Section~\ref{sec:practice}). Checks for benchmark authors and readers,
each with what it gave where we measured it, and a general method for a tool. The method takes the
kernel's timestamp of every packet on the client machine, which a tool can read on its own sockets
in four steps. It matches each message to its packets by the id that the broker gives it. From
those timestamps alone, a tool can check whether a request was waiting at the broker when each
message arrived. The latency between the kernel's timestamps held still across background load and
priority. We tested it at fifty messages a second on one pair of machines. Later tests, whose
predictions we committed before their runs, ran on two pairs of machines at $\gmRate$ messages a
second. On one pair, consumers that kept requests
waiting at the broker held the tail of that latency still under load on \redis{} and NATS. On
RabbitMQ, a consumer that gave the broker a standing permission to deliver more messages did the
same. On \kafka{}, one client has a fetch
thread that does nothing else. At real-time priority, that thread kept nearly all of the consumer's
own delay out of that latency. A broker can report the times that only it sees, in a few bytes per
message, when a consumer asks for them.
\end{enumerate}
Together, these results show that a broker latency below a millisecond describes both the broker
and how it was timed. They also give the means to time the broker alone.


\section{How a Message Is Timed}
\label{sec:sysmodel}
\label{sec:method}

A producer process publishes messages to a broker at a paced rate. A consumer process reads them
back. Each message crosses two legs (Fig.~\ref{fig:model}a). Leg~1 carries it to the broker. The
broker writes it to its log and returns an acknowledgment along leg~1. Leg~2 carries the message on
to the consumer. Three timestamps mark its path. The first is $t_{\mathrm{pub}}$, read immediately
before the publish call. The second is $t_{\mathrm{ack}}$, read when the producer learns that the
broker has accepted the message. The third is $t_{\mathrm{recv}}$, read when the consumer holds the
message. Their differences give three quantities:
\begin{equation}
\begin{aligned}
D &\equiv t_{\mathrm{recv}} - t_{\mathrm{pub}}, \qquad
A \equiv t_{\mathrm{ack}} - t_{\mathrm{pub}}, \\
S &\equiv t_{\mathrm{recv}} - t_{\mathrm{ack}} \;=\; D - A .
\end{aligned}
\label{eq:model}
\end{equation}
Broker benchmarks call $D$ the \emph{end-to-end latency}~\cite{openmessaging2018}. It is the
message's time from the publish call to the consumer. They call $A$ the \emph{publish latency}. It
is the producer's wait to hear that the broker has the message. $S$ compares the acknowledgment's return along
leg~1 with the message's trip along leg~2. On \kafka{}, the broker returns the acknowledgment
before it answers the consumer's waiting request. \redis{} writes the delivery to a waiting
consumer first.  A
benchmark that starts its clock at the acknowledgment reports $S$ as the message's latency. Every publish latency also carries whatever delays the reading of
its acknowledgment (Section~\ref{sec:toolsrun}). Two more readings place a message in its
workload. The reading $t_{\mathrm{sched}}$ is when the replayed schedule made it due, and
$t_{\mathrm{out}}$ is when the consumer had handled it. The \emph{event-time latency}
$E = t_{\mathrm{out}} - t_{\mathrm{sched}}$ holds $D$~\cite{karimov2018benchmarking}. The
\emph{publish delay} $t_{\mathrm{pub}} - t_{\mathrm{sched}}$ comes before $D$, and the consumer's
\emph{processing-time latency} $t_{\mathrm{out}} - t_{\mathrm{recv}}$ comes after it.

The measurements come from Oracle Cloud virtual machines on a private network, unless the text
says otherwise. One machine runs both brokers, \kafka{} and \redis{} Streams, each as a single node. \kafka{} has one partition and one replica, so \texttt{acks=all} is the leader's own append (Supplement~S1.2). Another machine runs the producer and the consumer as separate
CPython processes. It is the \emph{client machine}. The processes use the kafka-python and redis-py
client
libraries, and Supplement~S1 lists their versions where these were recorded. Both processes read
one clock, so nothing here depends on synchronizing clocks. The client machine's kernel is Linux~6.8, whose scheduler is EEVDF~\cite{stoica1996proportional}. EEVDF stands for Earliest Eligible Virtual Deadline First.

The producer replays StatsBomb's open football event data~\cite{statsbomb2023}, and only its
message sizes and rates matter here. Each message is a small JSON record of an event's identifiers and timestamps (Supplement~S1.1). In nine runs out of ten, a producer publishes
$\workloadRateLo$--$\workloadRateHi$ messages a second, as a sparse event feed does.   
\emph{Utilization}\label{def:rho} $\rho$ is the
fraction of processor time that is busy on the client machine over a run. The background load sets
it, and that load runs only on the client machine.

\label{def:vocabulary}A \emph{condition} is one point of the experimental design. It fixes a
broker, a publish rate, a message size, a background load and how often the consumer confirms what
it has read. A \emph{run} executes a condition once, and a \emph{replicate} is a further run of it.
A \emph{campaign} is a set of runs designed together. Some experiments change one variable and hold
the rest fixed. Each value that such an experiment gives the variable is a \emph{configuration}. A
later campaign ran on three pairs of Microsoft Azure machines, two x86 and one Neoverse~N2. It used the same brokers and the same clients. It also used \kafka{}'s Java client (Supplement~S1.1). It was \emph{registered}. We
committed its predictions to the project's public repository before the runs that test
them~\cite{nosek2018preregistration} (Supplement~S6.1). Two more registered campaigns, plan versions 47 and 49,
tested the general method of Section~\ref{sec:toolside} on two of these pairs (Supplement~S8). Supplement~S1.4 lists the runs behind each number.


\section{The Distribution of $S$}
\label{sec:finding}

On a broker that acknowledges first, $S$ is ideally a small positive margin
(Section~\ref{sec:proxy}). Measured, $S$ spreads over milliseconds, and part of it falls below zero
(Fig.~\ref{fig:twoways}). In the cloud runs that produced matched records, $\spanNegAckPct\%$ of the values of $S$ fall below zero (Fig.~\ref{fig:twoways}a).  This proportion is the share of $S$ below zero. It pools the runs of every
load. Each run counts in proportion to its number of messages. Per run, the share varies widely, and some runs have none (Supplement~S1.3). It rises with utilization and falls at real-time priority
(Fig.~\ref{fig:twoways}b). Both brokers show it (Supplement~S1.3). The registered campaign found
values below zero again with \kafka{}'s own Java client.  The campaign found them on Neoverse~N2 as on x86 (Supplement~S6.2).

to blame.

\section{The Mechanism and Its Laws}
\label{sec:mechanism}

A thread must wait for a core before it can read the clock. That wait is the thread's
\emph{scheduling delay}\label{def:scheddelay}. It is the time that a thread ready to run spends
queued before a core runs it. Real-time Linux measures it as scheduling
latency~\cite{bristot2025timerlat}. The kernel's timestamps and \emph{controlled experiments} show
when this wait puts $S$ below zero and when the broker's own order does. A controlled experiment
changes one variable and holds the rest fixed.

\subsection{When $S$ falls below zero}
\label{sec:proxy}
\label{sec:model}
$D$ and $A$ are causal chains. Each starts at the publish call, which comes before the broker's
write. The write comes before both the acknowledgment and the delivery. $S$ is not a chain.
Its two readings are two branches of one cause, the write, and neither has to come first.
Equation~\ref{eq:model} holds for every message, whatever the signs, so
\begin{equation}
S < 0 \quad\text{if and only if}\quad A > D .
\label{eq:negspan}
\end{equation}
If neither thread waited, $S$ would equal the \emph{margin}\label{def:margin} $m$. The margin is the
time that the message still needs to reach the consumer once the acknowledgment has reached the
producer. Each reading is late by its thread's delay, which holds any wait for a core
(Fig.~\ref{fig:model}b). So $S$ falls below zero when the acknowledging thread's delay,
$\delta_{\mathrm{ack}}$, is longer than the margin plus the consumer's own delay,
$\delta_{\mathrm{recv}}$. We measured the margin as $S_k = t_{\mathrm{rx}} - t_{\mathrm{rx,ack}}$.
It is the difference between the kernel's receive timestamps of the message and of its
acknowledgment.
No thread's delay enters $S_k$. On \kafka{}, the acknowledgment came first, by a median of
$\osKafkaMarginLoUs$--$\osKafkaMarginHiUs\,\mu$s.  Under load, $\osKafkaLatePct\%$ of the values of
$S$ below zero had $S_k \geq 0$, so they are late readings. On \redis{} with sixteen publish
workers, the delivery came first in $\osRedisFirstRuns$ of its $\osRedisRuns$ runs. \redis{}'s margin was then below zero,
and a value of $S$ below zero needed no wait. For $\osRedisOrderLoPct$--$\osRedisOrderHiPct\%$ of
its values below zero, the delivery had come first (Supplement~S3.11).


\subsection{How often, and what moves the share}
\label{sec:twostate}
\label{sec:mixture}
Each thread that reads the clock is either running or waiting for a core. A running thread's
reading is late by a narrow jitter. On \kafka{}, the share of $S$ below zero grows
$\invGrowth\times$ from an idle host to the heaviest load before its processors are fully busy.
Over the same range, the jitter's width only grows $\coreGrowth\times$. So load mostly changes how often the thread is waiting. Write $p$
for the probability that the thread is waiting for a core\label{def:occupancy}. Write $G$ for the
chance that the rest of its wait outlasts a given time. If the consumer's own wait is short, then
to leading order
\begin{equation}
\Pr\bigl[\,S<0 \mid m\,\bigr] \;\approx\; p\,G(m) ,
\label{eq:occupancy}
\end{equation}
the probability that the thread is waiting, times $G$ at the margin. This is the textbook decomposition of a wait, here read from the order of two clock
readings. Load, its placement and priority move $p$, and the path's length moves $m$.

\textbf{Priority.} Real-time priority for the threads that read the clock should lower $p$ while
utilization stays fixed. Every controlled experiment ran both brokers (Supplement~S3). Each controlled experiment
moved the share on both brokers. Real-time priority cut the share
$\rtFactorLow$- to
$\rtFactorHigh$-fold on \kafka{} and $\rtRedisFactorLow$- to $\rtRedisFactorHigh$-fold on \redis{},
over matched pairs at the same utilization.
It cut it at least $\rtKafkaLowerBound$- and $\rtRedisLowerBound$-fold in every pair, the smallest
of the pairs' run-level lower bounds (Supplement~S3.1). That refutes any account in which utilization alone sets the share, including
the queueing form we had ourselves adopted. In the registered campaign, on other machines,
real-time priority removed the values below zero on \kafka{} in every run. Load raised the share in
all five \kafka{} campaigns that tested it (Supplement~S6.2).

\textbf{Placement.} The background load was either concentrated on six of the \testbedCpusWord{}
cores or spread over all of them. The two configurations reached the same utilization, and on both brokers they gave different shares (Supplement~S3.2). On
\kafka{}, the spread load gave the higher share, $\GeomOrigFactor$-fold, and $\GeomReplFactor$-fold
in a full replication.  Spreading the load leaves no core free, so a woken
thread waits more often. On \redis{}, the concentrated load gave more values below zero. So where
the load runs matters on both brokers, in opposite directions.

\textbf{Path length.} A wait of a given size overlaps a short path almost entirely and a long one
hardly at all. Padding the payload lengthens the time to the consumer's reading, by transfer and
parsing, at nearly unchanged utilization. On \kafka{}, it raised the median of $S$
$\payloadTransportFactorRound$-fold. The share
fell $\payloadRateFall$-fold. On \redis{}, the share fell $\pathRedisOrig$-fold. That is the
direction $G$ predicts, and the opposite of what stress on the host would cause (Supplement~S3.3).

\textbf{The wait, timed message by message.} The registered campaign timed each acknowledgment's
own wait for a core (Supplement~S6.1). Of the
readings below zero, $\recMostlyWaitingLo$--$\recMostlyWaitingHi\%$ had spent most of the time from
the reply's arrival to the timestamp waiting for a core. With nothing fitted, we predicted the
share of $S$ below zero from the share of acknowledgments whose own wait outlasted the run's
margin. At the median, the predictions were $\recOwnWaitRatioLo$--$\recOwnWaitRatioHi$ times the
measured share. The registered prediction held on
\recOwnWaitPartsInWord{} of the \recOwnWaitPartsWord{} pair and broker combinations
(Supplement~S6.2). In the runs timed by the kernel, load raised the 99th percentile of the acknowledging thread's delay on both brokers, and real-time priority brought it back near its idle value (Supplement~S3.11). Our
earlier kernel trace of every thread's wakeups~\cite{gregg2016runqlat} is consistent with the
mechanism. At every threshold we read it at, around \kafka{}'s median of $S$ with no load, its share of longer waits stayed inside the factor of three fixed before it was read (Supplement~S3.5).

\subsection{The timescale the slice sets}
\label{sec:tail}
A thread woken while another holds the core waits out what is left of the running
thread's \emph{slice}. The slice is the time the scheduler lets a thread run at a turn. A woken
thread can wait up to a whole slice, because the scheduler does not preempt the running thread for
it before that slice is spent. The kernel checks for a spent slice only at each \emph{tick} $h$  of its timer. So the wait can run up to a tick past the
slice. The kernel sets the base slice $s$ from the CPU count $n$, with a cap:
\begin{equation}
s \;=\; s_0\times\bigl(1+\lfloor\log_2\min(n,8)\rfloor\bigr),
\label{eq:slice}
\end{equation}
where $s_0$ is $\sliceConstantMs$~ms on the kernels we ran (Supplement~S3.7). That
gives $\sliceFactor \times \sliceConstantMs$~ms $= \baseSliceMs$~ms on our hosts'
\testbedCpusWord{} CPUs. The traced waits carry that timescale. They have several local maxima, which survive wider buckets. The last one sits in the bucket that contains the slice, and above it the counts collapse (Supplement~S3.7). The trace also counts waits that
begin when a thread is preempted, and these last about a whole slice. The thread that reads the
acknowledgment is instead woken by the reply. Its own wait is the rest of a slice
(Fig.~\ref{fig:residual}). The registered campaign timed this wait, and we read it after its
predictions were judged.

\subsection{The same wait delays a consumer's next request}
\label{sec:laterequest}
A pull consumer asks the broker for each batch of messages, as \kafka{}'s and \redis{}'s consumers
do. One that keeps one request at a time asks again only after its thread has handled the last
answer. If that thread must first wait for a core, the next request waits too. A message that
reaches the broker while no request waits there
stays at the broker until the next request comes. That wait at the broker enters even a latency
timed by the kernel. Let $W$ be the latency from the kernel's transmit timestamp of the message to
the kernel's receive timestamp of its delivery. The message leaves the broker only when the next
request arrives, so its wait at the broker is part of $W$. Later registered campaigns measured this on \redis{} and \kafka{}. The background load was switched on and off within each run (Supplement~S8). The tail of
a quantity here is its mean, in each load state, over the $1\%$ of messages with the largest $W$.
On \redis{} with one request at a time, the load raised the tail of $W$ $\gmRaWRatio$-fold. In each of four \kafka{} clients at normal priority, at least $\gmKCbSharePctLo\%$ of the load's rise in the tail of $W$ was time in which the message waited at the broker for the client to ask again (Supplement~S8.1). So a client thread's wait enters a
latency in two places: in its clock readings and in its requests.


\section{An Industry-Wide Audit}
\label{sec:external}

Across the industry, the tools we audited delete, replace or never measure a latency at or below
zero, and almost never count it. The wait for a core enters a latency in two places (Section~\ref{sec:laterequest}).
Sections~\ref{sec:tools} to~\ref{sec:extmethod} cover the first, the clock readings: what tools
do with values at or below zero. Section~\ref{sec:brokeraudit} covers the second, the requests:

most when a message arrived, or how long it stayed at the broker in milliseconds
(Section~\ref{sec:brokeraudit}).
We read
\harnessAuditedWord{} tools at source, ran \toolsRunWord{} under registered predictions, measured
one benchmark's filter in depth and audited the public reports made with it. We also read what

\subsection{A filter on a millisecond clock}
\label{sec:extmethod}
\label{sec:extphase}
\label{sec:extcomp}
One of the cuts above is a filter that keeps only latencies above zero. It is the one cut that
deletes more than the values below zero. In statistical
terms it truncates the distribution at zero. What it removes is not counted, as it would be if it
were censored. We measured it in
depth in a broker benchmark whose end-to-end percentiles $\reachReports$ public reports print, the
OpenMessaging
Benchmark~\cite{openmessaging2018}. Its filter was added in 2018 because its end-to-end latency
``is calculated based on time difference of \texttt{System.currentTimeMillis()} on two different
machines'' and ``can be negative''~\cite{openmessaging_pr56}. Its histogram rejects values
below zero outright. For clocks that disagree, the filter is a sound local fix.

It has two side effects. Its clock counts whole milliseconds (Supplement~S5). So its \emph{timestamp resolution}
$\tau$ is a millisecond. The timestamp resolution is the smallest step a timestamp can take. A
message that arrives before
the millisecond digit changes therefore computes to zero and is deleted (Fig.~\ref{fig:deletion}a).
Nothing counts what the filter deletes. A sample survives only if a millisecond boundary falls between its two timestamps. With publish instants placed uniformly within the millisecond, that happens with
probability $T_{\mathrm{true}}/\tau$ on a path shorter than $\tau$. Here
$T_{\mathrm{true}}$\label{def:ttrue} is the \emph{true end-to-end latency}. It is the latency that
a perfect clock, read without delay, would give. So the share of samples kept is
\begin{equation}
\label{eq:retention}
\text{share kept} \;=\; \min\!\left(1,\; \frac{T_{\mathrm{true}}}{\tau}\right) .
\end{equation}
Every sample kept on such a path reads exactly one step. So two brokers whose messages all
arrive within a millisecond print the same median. They differ only in the share of samples they
keep, which is never printed. The arithmetic is in Hewlett-Packard's 1970 counter note~\cite{hp1970tia}, but the
deletion is not. That counter keeps its zero readings.

We added counters that record, by sign, every sample the filter discards, and changed nothing
else.  Of the $\ombMedianCells$ settings whose own summary we captured,
$\ombGridMedianCells$ printed a median of exactly $\ombGridPrintedLo$ or $\ombGridPrintedHi$~ms,
computed from $\ombGridRetentionMin$--$\ombGridRetentionMax\%$ of the samples
(Fig.~\ref{fig:deletion}b). Two
replicates of one setting kept $\ombKeptLo$ and $\ombKeptHi$ samples, $\ombRetentionFold$-fold
apart, and printed the same median. The filter can also inflate a median. When it deletes the fast samples, it prints the median
of the slow remainder (Supplement~S4.3).

Equation~\ref{eq:retention} holds where it can be tested. A publish rate is \emph{incommensurate} with the clock when its interval bears no ratio of small whole numbers to $\tau$. Every configuration at such a rate keeps about the same share (Supplement~S4.2).

Counted by sign, the filter hides two failures. On \kafka{}, the $\ombKafkaDiscarded$ samples it
discarded over $\ombKafkaRuns$ runs hold $\ombKafkaNegatives$ values below zero. Each of those
samples computed to zero, lost to the clock's step. On \redis{}, the benchmark subtracts the
broker's millisecond timestamp from the consumer's clock. There all $\ombRedisNegatives$ values
below zero in $\ombRedisRuns$ runs were exactly $-\tau$, the mark of two floored clocks less than a
millisecond apart (Supplement~S4.4).

\textbf{Public reports.}\label{sec:reports} We also audited the benchmark's public reports (Supplement~S5). The audit looked for the deletion's signature, a printed
end-to-end median of exactly 1~ms. Of the $\reachMedianConfigs$ end-to-end medians in
$\reachReports$ reports, \reachPrimaryConfigsWord{} carry it, in \reachPrimaryReportsWord{}
reports. No report states how many samples it kept. The signature is rare partly because
$\reachFinerReports$ reports come from copies with a finer clock (Supplement~S5).

\subsection{What brokers tell a consumer and a producer}
\label{sec:brokeraudit}
A message can wait at the broker for the next request (Section~\ref{sec:laterequest}). The time it
waits there enters $W$. Only the broker sees when that time starts and when it ends. So a tool
can take that time out of $W$ in two cases only. In the first, the broker reports how long the message waited,
or the two times on its own clock. In the second, no message waits, because a request or
\emph{credit} from the consumer waits at the broker for every message. Credit is a consumer's
standing permission for the broker to deliver more messages without being asked again, such as a
prefetch count.

We audited which brokers allow either case. The audit covered every broker that one of the audited tools can time, the three largest clouds' own message services, and the established brokers that a wide search found. That makes $\baBrokers$ brokers. An \emph{interface} is one way to consume or to publish, such
as pulling and pushing. The brokers have
$\baConsumerModes$ consumer interfaces and $\baProducerModes$ producer interfaces. 

Supplement~S7 sums up the answers in a table, interface by interface. Of the consumer interfaces, \baWaitModesWord{} report
the time a message waited for its request, and neither is a production broker as it ships. One is
Zenoh's storage queries, through a timestamp feature that its code marks unstable. The other is
Azurite, an emulator of Azure Queue Storage, to the second. $\baStayModes$ interfaces in
$\baStayBrokers$ brokers report the message's \emph{residence time}. This is its whole time at the
broker, from its arrival until the broker hands it on. It is the message's time waiting for its request
plus the broker's own handling. So it bounds that time from above. Among the brokers that the industry's tools time, those that report it do so in milliseconds at best (Supplement~S7).
The other interfaces tell the consumer at best the message's arrival time (Supplement~S7).

Many brokers already keep the times that a tool needs. $\baKeptRequestModes$ interfaces in
$\baKeptRequestBrokers$ brokers record when each request arrived and keep that time inside. \kafka{}'s fetch is among them. Such a broker
could report the time with each message without measuring anything new. In $\baWaitCan$ of the
$\baConsumerModes$ consumer interfaces, a consumer can keep a request or credit waiting for every
message. \kafka{}'s fetch is not among them. Its broker holds one request at a time from each
connection. So a message that arrives between an answer and the next fetch waits for that fetch.

The producer's side has the same gap. Suppose that an acknowledgment carried the time the broker
received the message and the time it acknowledged it. Then a producer could take the broker's own
time out of its round trip without sharing a clock with the broker.  Only \baHoldModesWord{} producer interfaces  carry both times (Supplement~S7).

So for every broker that the industry's tools time, a tool can know exactly how much of $W$ a
message spent waiting at the broker for a request only where a request or credit waits for every
message.

every tool how long each message waited at the broker (Section~\ref{sec:brokerreport}).

\subsection{The tools' side: a general method}
\label{sec:toolside}

\textbf{Let the kernel timestamp each message.}\label{sec:fix} A tool reads each of a message's
timestamps in one of its threads, which may first wait for a core. The kernel timestamps
each packet as it leaves and enters a machine, the transmit and receive timestamps,
without waiting for any program's thread. The latency $W$, from a message's transmit timestamp to
its receive timestamp, therefore holds the network and the
broker but no client thread's wait, whenever each socket read drains one packet and a consumer
request already waits at the broker. No wait is lost:
$H_{\mathrm{out}}$ runs from the publish call to the transmit timestamp and $H_{\mathrm{in}}$ runs
from the receive timestamp to the consumer's reading, so
$D = H_{\mathrm{out}} + W + H_{\mathrm{in}}$ for every message (Fig.~\ref{fig:kernel}). This
is network measurement's rule: delay is defined between times on the wire, not
the host times a program reads~\cite{rfc2330}, and the one-way delay standard bounds each host's
share by terms that $H_{\mathrm{out}}$ and $H_{\mathrm{in}}$ measure~\cite{rfc7679}. A tool takes
these timestamps from its own sockets where its language allows, or else from a packet capture on
the client machine, with no change to the client. It names each message by the broker's own id,
such as a \kafka{} offset or a \redis{} entry id. 

All five predictions of the fix's first test, fixed before any run, held. Over $\fullFixRuns$ runs on both brokers, timed
from packet captures, the median of $W$ moved at most $\fullFixMedianMovePct\%$ and its 99th
percentile $\fullFixTailMovePct\%$ across load and priority, inside the bands fixed before the runs. Their run-level intervals reach beyond the bands, so the bands hold for the point estimates only (Supplement~S3.9). In the same runs, load at normal priority raised the 99th
percentile of $D$ $\fullFixTailRatioLo$--$\fullFixTailRatioHi$-fold. A delay added between broker and consumer raised $W$ by about as much as the delay (Supplement~S3.11). $W$
never reached zero, so a filter that keeps only latencies above zero deletes nothing from it.

\textbf{Read those timestamps on the tool's own sockets.} A tool need not capture packets. On
Linux it reads these timestamps through the \texttt{SO\_TIMESTAMPING} \emph{socket option},
a setting a program makes on a socket, in four steps~\cite{linux_timestamping}, whose settings Supplement~S3.10 gives in full. \begin{enumerate} \item On each connection to the broker, before its first write, turn on the kernel's software timestamps for transmit and receive. \item Read each write's transmit timestamp from the socket's \emph{error queue}, where the kernel leaves it. Read the error queue at every write and read, since while it holds a timestamp a client that polls the socket spins.
\item Take the receive timestamp the kernel returns with each read, that of the last packet the
read consumed.
\item Find each message in the bytes by an identifier the benchmark puts in each payload; this
needs a connection without compression or encryption. Time it from the transmit timestamp of the write
that carried it to the receive timestamp of the read that delivered it. Report that latency beside
$D$, and count any message left without a timestamp.
\end{enumerate}
Lancet reads a request-reply service's timestamps this way~\cite{kogias2019lancet}, Fathom
splits a fleet's call latency into host and network parts with kernel
instrumentation~\cite{qureshi2023fathom}, and Zuo et al.\ split a host's network-stack latency at
kernel timestamps~\cite{zuo2026hoststack}. We read these timestamps beneath unmodified broker
clients, on the one-way path from producer to consumer. Our Python module takes these steps for
both brokers (\brk{scripts/so_timestamps.py}). In $\soFixRuns$ more runs it came
within $\soFixAgreeMedianHiUs\,\mu$s of the captures' latency at the median. Both read the kernel's
receive timestamp, so this shows the module matches timestamps to messages. The network card's own timestamps bound how far the kernel's timestamps lie from the wire (Supplement~S3.9). Under load at
normal priority, the tail of $D$ again grew $\soFixTailRatioLo$--$\soFixTailRatioHi$-fold, while
the latency the module timed held level (Fig.~\ref{fig:fixbenefit}).  Against the
capture runs, taking the timestamps moved the clients' own time, $D - W$, and the 99th percentile of $D$ by less than a fifth of a millisecond either way, the drift between two days included (Supplement~S3.10). The sockets agreed with the captures up to $\osTopRate$ messages a second (Supplement~S3.11).

\textbf{What a tool must handle.} A read that drains several packets times the earlier ones late,
by their wait in the socket, which is the consumer's wait. A pull consumer, which asks the broker
for each batch as \kafka{}'s and \redis{}'s do, adds another: a message the broker stores while no
request is outstanding waits for the next one, which the consumer's thread issues after its own
wait, inside $W$. A tool can flag such messages, those delivered in answer to a request whose
transmit timestamp follows the message's own; Supplement~S3.11 counts them at each rate. Where
receive processing runs
in a kernel thread, the receive timestamp waits for a core too (Supplement~S3.9). Under
threaded network polling, for example, a kernel thread polls the network card. The kernel's
deferred interrupt work, the softirq, also moves to kernel threads, \texttt{ksoftirqd}, when it
falls behind. Where a driver
gives no software transmit timestamp, as on our cloud's accelerated network, the transmit timestamp left to a tool is taken before the packet scheduler, so any queueing there falls inside $W$ (Supplement~S3.10). With producer
and consumer on two machines, $W$ spans two clocks and includes their offset, so they must be
synchronized well below the latency. A design in which the consumer acknowledges back to the
producer times two legs on one clock, not the one leg wanted. Recovering the two clocks' offset
from logs instead is itself synchronization. Java's standard sockets expose neither the option nor
the error queue, so a Java tool needs a native call (Supplement~S3.10). A kernel-bypass stack
has no kernel timestamps at all. A tool that cannot yet take them needs the checks of
Section~\ref{sec:checklist}.

\textbf{Check whether a request was waiting.} The same timestamps can settle, for each message,
whether a request or credit was waiting at the broker on its arrival, wherever a bound on the
network's delays allows (Supplement~S8.2). A tool reports the share of
messages that found none beside the latency. Plan version 47 tested this reading. In each run that it judged, the reading never said that
a message found none when the broker's own capture showed one waiting.  In plan version 49, in each run whose own checks held, the clients'
own timestamps showed a waiting request or credit for every message. That held on \redis{}, on
NATS JetStream and on RabbitMQ (Supplement~S8).

\textbf{Report three latencies.} $F$ is the latency to a receiver as ready as the protocol
allows: what the broker and the network deliver when a request already waits, or, on \kafka{}, when
the client asks again at once. $W$ is the latency to the consumer's kernel, and $D$
the latency to the application. $W - F$ is the client's part, its wait to ask again. $D - W$ is the
time spent in the two clients, $H_{\mathrm{out}} + H_{\mathrm{in}}$, their threads' waits for a core
included.

\textbf{Keep a request or credit waiting, by protocol.} Where the protocol allows it, the consumer
should ask ahead: it keeps enough requests or credit at the broker that each arriving message finds one. Then no message waits for
the next request, so $W$ holds none of the client threads' waits. Plan version 49 tested this (Supplement~S8). On \redis{}, NATS JetStream and RabbitMQ, the tail of $W$
then held still under the load, while $D$, over its own largest $1\%$ of messages, grew $\gmDGrowLo$- to $\gmDGrowHi$-fold. \kafka{}'s broker holds one fetch at a time from each connection. There the
remedy is a fetch thread that does nothing else, raised to real-time priority. In librdkafka, the
broker thread is such a thread. With that thread raised, the client's part, over its own largest $1\%$, rose under the load by at most $\gmQbSharePct\%$ of its rise at normal priority, on both pairs (Supplement~S8.2). The fetch's round trip stays in $W$, and it is real latency. All
$\gmLaterPredictions$ predictions of plan version 49 held (Supplement~S8). They were chosen after
reading plan version 47's runs of the same setups, and every one held on those runs, so the new runs
are their only test. Plan version 47's own test of the held tail of $W$ was not confirmed. The tail
held still, but the load raised $D$ less than that test required
(Supplement~S8.2).

\subsection{Checks for benchmark authors and readers}
\label{sec:checklist}

\textbf{Check every run for values below zero.}\label{sec:gate}\label{sec:audit} The \emph{check
for values below zero} rejects a
run when more than one percent of its messages carry a value below zero in any latency component it
records ($S$, the publish delay or the processing-time latency), or when the median of any of them
is below zero. It rejected $\auditPctCloud\%$ of the cloud runs behind our results (Supplement~S2). It sees only the worst cases: the publish latency
exceeds half the end-to-end latency on $\diseaseOverHalf\%$ of messages, but the check is triggered
only by the $\diseaseOverWhole\%$ on which it exceeds the whole, and a latency that load inflates
but leaves positive passes the check by construction. The check also assumes a broker that acknowledges no
later than it delivers. On one that delivers first, as \redis{} often does, a value of $S$ below
zero needs no wait, so there it should read only the differences timed from the publish call. The check therefore needs the
repair that follows.

\textbf{Time from the publish call, or add the publish latency back.}\label{sec:cost}
The repair is Equation~\ref{eq:model}: $D = S + A$ for every message, and $A$ is read on the producer's side of
the same clock, so a benchmark that records its publish latency recovers each message's end-to-end
latency exactly. Error arises only where a benchmark keeps summaries. Over groups of runs,
the median of $S$ plus the median of $A$ misses the median of $D$ by a median of $\recoveryErrKafka\%$ on \kafka{} and $\recoveryErrRedis\%$ on \redis{} (Supplement~S2.1). The check's verdict made no detectable difference to that error on either broker.
The publish latency does not grow as leg~2 lengthens. On one path, the relative error of $S$ as a latency, $A/D$, therefore falls
as $1/D$. 
Below $D = \exposureCrossover$~ms
the publish latency exceeds $D$ itself. From one condition to the next, though, \kafka{}'s $A$ grows with $D$, so its groups lie above that curve (Supplement~S2.1). Timing from the publish call removes
the values below zero, but not the consumer's own wait for a core, which lengthens every latency,
unseen by any check. In our runs it added $\recvWaitAddedLo$--$\recvWaitAddedHi$~ms to the mean of $D$ (Supplement~S3.8), a wait that $W$ leaves out.

\textbf{Give the threads that read the clock a core.} Real-time priority cut the share of $S$
below zero in every matched pair. At real-time priority some values of $S$ below zero
remain (Supplement~S3.1), so the check stays. A real-time or spinning thread also changes the system it measures.

A better-synchronized clock repairs neither the late reading nor the deletion: the values of $S$
below zero arise on one clock, and the deletion from the clock's step. A finer clock confines the
deletion to faster paths but leaves the filter and every value of $S$ below zero in place. The
remedies are therefore ordered: record at native resolution, count what is discarded and randomize
the publish instants, and only then improve the clocks' synchronization.

\subsection{The brokers' side}
\label{sec:brokerreport}
A broker sees when a message starts to wait for its request and when the request arrives,
so it can measure that time exactly.
It should report, with each message it delivers, how long the message waited: from the moment the
message could be delivered to the arrival of the request or credit that took it. It should take
both readings on its own monotonic clock, on the node that serves the request. Written as a variable-length integer of microseconds, that time takes at most three bytes below $\baVarintThreeUs\,\mu$s (Supplement~S7.1). 
With that time reported, every tool can take each message's wait for its request out of $W$,
whatever the protocol.

Where the time goes matters. A broker such as \kafka{} keeps its batches with a checksum and passes
them from its files to the network unchanged, so a time per delivery belongs in the envelope of the response, not
inside the stored batch. It should be a numbered field, not a named header. Names cost bytes, and different brokers give one time different names (Supplement~S7.1). A broker should add the field
only when a consumer asks for it, since an unrequested field can break older clients (Supplement~S7.1).

For the producer, each acknowledgment should carry two times: when the broker received the
publish and when it acknowledged it. The Network Time Protocol (NTP) gives its clients a server's two times in the same way,
and \baHoldModesWord{} of the producer interfaces we audited already do
(Section~\ref{sec:brokeraudit}).

\section{Related Work}
\label{sec:related}

\textbf{Scheduling delay.} That a ready thread can wait for a core is well
known~\cite{gregg2016runqlat}. Behind another thread's slice, the wait adds milliseconds to a
server's tail latency, and real-time priority removes it~\cite{li2014tales}. Co-located work
lengthens it~\cite{leverich2014reconciling}, a longer slice extends it~\cite{jia2024skyloft}, and
real-time Linux measures it as noise~\cite{bristot2023osnoise}. In Linux's network stack, the time
a reader woken by arriving data waits to run is the main source of tail
latency~\cite{zuo2026hoststack}, and the limits of the timers that benchmarks read are known
too~\cite{kuperberg2011timers}. Load testers of microsecond-scale services correct for the
\emph{client bias} that their own queueing and scheduling add~\cite{zhang2016treadmill,kogias2019lancet}.
Villain et al.\ found that an outgoing socket timestamp ``does not respect causality'' under every
stress pattern, including none~\cite{villain2012probing}. None gives the consequence for a
difference read by two processes: its share below zero is set by $p$, the probability that the
thread is waiting for a core, and by the margin, on the timescale of the slice.

\textbf{Clocks.} Across hosts, values below zero are read as clocks that disagree, and on one host
as a thread preempted after it read the clock~\cite{mckenney2023perfbook}, but neither reading
measures the share or its laws. Sharma et al.\ read negative timing spans as clock skew, since
``queueing alone cannot produce negative timing spans''~\cite{sharma2026causality}. For the backlog
they model we agree, but a timestamping thread waits in a second queue, the kernel's run queue.
Van Dongen and Van den Poel, seeing latencies below zero on up to a tenth of their events, took
both timestamps from one broker~\cite{vandongen2020evaluation}, the one-clock rule reached by
another route. Network measurement defines delay between wire times~\cite{rfc7679}, and Lancet and
Fathom read such times through the kernel~\cite{kogias2019lancet,qureshi2023fathom}. We read them
beneath unmodified broker clients.

\textbf{Resolution and discarded samples.} The arithmetic of the share kept and its cure, phase
jitter, are in a 1970 counter note~\cite{hp1970tia}, and a clock coarser than the intervals it
times can still estimate their mean~\cite{danzig1990highres}. IP measurement advises randomizing
probe times~\cite{rfc2330,baccelli2006pasta}, since a periodic schedule can synchronize with
periodic behavior~\cite{rfc3432}, here the clock's step. Coordinated omission~\cite{tene2015latency}
is the deletion's mirror image: it fails to record samples that would have been slow. Network
measurement reports the share of traces it rejects~\cite{paxson1998calibrating} and keeps a packet
timestamped in the future~\cite{rfc4656}, and rigorous benchmark reporting asks that removed
outliers be counted~\cite{georges2007rigorous,hoefler2015benchmarking}. The tools we audited
remove samples before any analyst sees them and count none, a case that neither that literature
nor the principles for reproducible performance evaluation in the
cloud~\cite{papadopoulos2021methodological} address. Stream-processing benchmarks compute latency
from \kafka{}'s millisecond timestamps of a record and of its result~\cite{henning2024shufflebench},
so the same arithmetic applies wherever their latencies fall below a millisecond. We add these
checks, applied where a benchmark reports a latency.


\section{Limitations}
\label{sec:threats}
\label{sec:limitations}

That scheduling makes \kafka{}'s readings late is now observed message by message
(Section~\ref{sec:twostate}). One clock excludes clock skew, and the controlled experiments exclude
utilization and stress. Real-time priority excludes the interrupt noise that reaches every
scheduling class, while timer slack, which differs between classes, cannot delay a wakeup on
arriving data. Clocks that disagree across virtual CPUs are excluded too. On the Oracle machines a
clock whose read costs at most $\clockIncrementNs$~ns can only be one the kernel uses where the
CPUs' clocks agree. The Azure machines read the processor's timestamp counter, which the kernel uses
as its clock only where the counters agree (Supplement~S3.6). Since $D$ never fell below zero, no
offset can exceed its smallest value, $\spanOffsetMargin$ times smaller than the deepest value of
$S$. Both testbeds are virtual, so \emph{steal time}, the time a virtual processor is ready but
waits while the hypervisor runs another machine, is bounded, not excluded: real-time priority, a
setting inside our virtual machine, cannot shorten it, yet it cut the share. On the Oracle
machines, our \kafka{} and \redis{} clients ran side by side, so each broker's numbers there
include the other's clients in the load (Supplement~S1.1). The rival we had left open, a broker
that delivers before it acknowledges, is real on \redis{} and rare on \kafka{}
(Section~\ref{sec:proxy}). By our registered rule, \redis{}'s values of $S$ below zero with the
delivery first count as its reply order, though the readings' delays still decide which
delivery-first messages fall below zero. That order lets \redis{}'s real-time share stay above zero:
across the matched pairs it stayed near two percent at every load, while the normal-priority share rose by about two-fifths (Supplement~S3.1). Our CPython
timestamps also wait on the interpreter lock, and \kafka{}'s Java client, which has none, shows
values below zero too, at a third to a quarter of Python's share (Supplement~S6.2), so the effect
needs no lock. With one publish worker instead of sixteen, \redis{}'s real-time share fell more than thirtyfold with no load, so there the lock the workers share
sets most of it, though not under load (Supplement~S3.11). We have not tested why placement moves
the two brokers' shares in opposite directions, nor traced the cause of \redis{}'s mode near
$-\osBumpMidUs\,\mu$s in Fig.~\ref{fig:twoways}; on a second pair, a processor waking from idle
did not cause it (Supplement~S3.11).

Equation~\ref{eq:occupancy} describes how the share moves between conditions. Inside one, the share
rises with $D$ in $\rbdUp$ of $\rbdTestable$ testable conditions, because a long delivery comes with
a long publish latency (Supplement~S3.4). A registered prediction that priority would cut $p$ at
least tenfold failed: by the scheduler's counters, which average away the tail, it fell only about twofold, so the equation's factorization is untested
between conditions. In the registered campaign, none of three predictions of the share from
recorded waits held within the registered factor of $1.5$ on every pair and broker. The share of
readings below zero whose thread had mostly been waiting reached the registered $90\%$ on
\recMostlyWaitingHoldsWord{} of \recMostlyWaitingPartsWord{} combinations. The law's fitted shape
placed the fall in the slice's band less often than the free reading, and at no CPU count on
\redis{}. No prediction of where the share falls at a hand-set slice passed both readings, and
those of how quickly it falls held on one broker at most (Supplement~S6.2). Nor, with the margin
read on the kernel's timestamps, did the share fall from each fifth of the margin to the next, as
registered. Turning off the scheduler's run-to-parity rule, which lets a running thread keep its
core until its slice is spent, moved neither the share nor the acknowledging thread's delay,
against a registered cut to two-thirds, so the rule alone does not hold a woken thread off the core
(Supplement~S3.11). The kernel trace pools both brokers' threads and is not free: under it
\kafka{}'s real-time runs read no value below zero, against $\untracedRtNegatives$ in
$\untracedRtEvents$ untraced. The traced real-time configurations therefore cannot test the trace
check, though under the trace the normal-priority share did not move (Supplement~S3.5). The
registered campaign's recording raised the share it recorded up to about fourfold, so each prediction is held against its run's own share. The base slice on the
Oracle hosts is derived, not read off them; the Azure hosts read it back. The constants are those
of one EEVDF-era kernel, before Linux~6.17 limited the run-to-parity rule, a change for threads that
set their own slices. The distribution and the laws were measured with paced producers at about one
message a second each, and fifty messages a second in the registered campaign, where the threads
that read the clock sleep between messages and must be woken. At $\osMidRate$ messages a second on
an idle host, \osMidSplitRunsWord{} of \osMidRunsWord{} runs had most values of $S$ below zero for
the whole run. The laws were not tested above fifty messages a second (Supplement~S3.11). The late
request (Section~\ref{sec:laterequest}) was shown on one x86 pair, for \redis{} and \kafka{} only.
On NATS and RabbitMQ, the consumers we tested fell behind $\gmRate$ messages a second, so the
test could not show it (Supplement~S8.1). The rule that leaves out messages delayed by
a testbed fault was chosen after the Oracle testbed was gone (Supplement~S1.5).

The fix was tested from packet captures and, through a Python module, on the clients' own sockets.
Those tests used one pair of machines and one kernel, with one partition, background load on the
client machine alone, and the producer and the consumer on one machine. Its stillness under load
was judged at fifty messages a second only. On a second pair, under load, \kafka{}'s $W$ held
within $\osLadderKafkaMovePct\%$ and \redis{}'s rose $\osLadderRedisRisePct\%$. At $\osTopRate$
messages a second, with nearly every message flagged, a pull
consumer's wait entered $W$. On that virtual network a departing packet's timestamp came only from
before the packet scheduler, and the clients used neither encryption nor compression. We tested no
designs that timestamp in hardware or pin a spinning thread to its own core
(\emph{busy-polling}), which keep the waiting state out of the latency they time. The general method was tested at $\gmRate$ messages a
second on one x86 and one Neoverse~N2 pair, with the load only on the client machine. Plan version 47
confirmed \gmFirstConfirmedWord{} of its $\gmFirstPredictions$ predictions, did not confirm
\gmFirstNotConfirmedWord{} and could not judge \gmFirstNotJudgedWord{}. RabbitMQ's credit was shown waiting
only at a bound of $\gmBetaWideMs$~ms (Supplement~S8.2).

The deletion is demonstrated in one benchmark, in its embedded mode, and reproduced in an
independent program of ours; the benchmark's distributed mode, run on the Azure machines, dropped
values below zero under a moved clock, uncounted (Supplement~S4.5). In the registered change of
message size (Supplement~S4.3), the $32$~KB configuration pinned at a share kept just above the predicted two-thirds. The audit found the deletion's
signature in few public results, so we claim it for those and our own runs only. We chose the tools
in rounds, not by sampling, classified the \harnessAuditedWord{} tools by reading them, and ran the
\toolsRunWord{} tools on a single kernel and machine pair, at one publish rate. The broker audit ran no
broker. It read sources only, and it left the products below its scope rule unchecked
(Supplement~S7). The brokers' side of Section~\ref{sec:brokerreport} is a proposal that we have not
built. How much a deployment loses depends on its end-to-end latency and publish rate, so we
recommend reporting the share of samples kept rather than calling any reported number wrong.


\section{Conclusion}
\label{sec:conclusion}

A latency benchmark measures the system only while the delay before each reading is short beside
the latency it measures. On one machine's clock, the moment a producer reads a broker's
acknowledgment and the moment a consumer reads the message can differ by milliseconds, in either
order. A thread waits for a core, for up to a scheduler's slice, before it reads the clock, and a
broker that delivers first needs no wait. That wait can also postpone a pull consumer's next
request and hold the message at the broker meanwhile. Across the industry, values at or below zero
are deleted, replaced or never measured. Where the clock counts whole milliseconds, discarding every
value at or below zero also discards the fastest messages, and no report we audited says how many
samples it kept. None of the brokers those tools time reports how long a message waited for its
request, or a residence time finer than a millisecond. On Linux a tool can time each message
between the kernel's timestamps, read on its own sockets, and report that latency beside the
end-to-end latency. At fifty messages a second, the latency between the kernel's timestamps held no
client thread's wait. The same timestamps can show whether a message found a request or credit
ready at the broker, and a broker could add, in a few bytes, how long each message waited for one. Before
acting on a broker latency below a few milliseconds, ask what it
was timed from, how many samples the tool kept, and how many it discarded, by sign.
